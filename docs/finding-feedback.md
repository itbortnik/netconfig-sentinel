# Обратная связь по находке

Оператор может подтвердить аномалию, отметить ложное срабатывание или оставить
её на проверке. Оценка сохраняется отдельно от исходного анализа: findings,
объяснения, confidence, anomaly_score, risk и модель не переписываются.
Это мнение владельца общего service-токена, не подтверждённая личность инженера,
не разрешение на применение патча и не проверенная ground-truth метка датасета.
Обратная связь не запускает обучение и не становится training label автоматически.

## Схема и запуск

Настройте постоянный API по [инструкции](persistent-api.md). Для существующей БД
сделайте резервную копию вместе с безопасно сохранённым прежним ключом и выполните:

```powershell
python -m app.db.migrate
```

Revision `0003_finding_feedback` добавляет таблицу оценок и индекс истории;
upgrade с `0001_initial`/`0002_model_registry` сохраняет снимки, анализы,
реестр моделей и аудит. Startup не меняет схему. Не создавайте новый ключ для
старой БД. Повторный upgrade безопасен; destructive downgrade не поддерживается.

## Контракт

Все запросы требуют `Authorization: Bearer <token>`.

`POST /api/v1/findings/<finding_id>/feedback` принимает только JSON:

```json
{
  "feedback_id": "00000000-0000-0000-0000-000000000005",
  "analysis_id": "00000000-0000-0000-0000-000000000001",
  "finding_sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "verdict": "needs_investigation",
  "comment": "Проверить допустимость настройки в этой площадке."
}
```

Это пример формы, не существующая находка. Возьмите `analysis_id`,
`finding_id` и соответствующий `explanations[].finding_sha256` из сохранённого
результата анализа. UUID находки может повторяться в разных запусках, поэтому
UUID анализа обязателен; hash связывает мнение с точным содержимым находки.
Создайте новый `feedback_id` один раз для нового намерения и сохраняйте его
при повторе той же отправки после обрыва связи.

Допустимые verdict:

| Значение | Значение в интерфейсе |
| --- | --- |
| `confirmed_anomaly` | Аномалия подтверждена |
| `false_positive` | Ложное срабатывание |
| `needs_investigation` | Нужна проверка |

Comment обязателен: 1–2000 Unicode-символов, без крайних пробельных символов
и управляющих знаков, кроме CR/LF/TAB внутри. UI удаляет крайние пробелы перед
отправкой; HTTP-клиент должен передать уже нормализованный текст. Не вписывайте
секреты, полные конфигурации или персональные данные. Лимит JSON-body — 16 KiB;
неизвестные поля, повторные ключи, сжатые тела и произвольный `actor` запрещены.

Ответ `finding-feedback-0.1.0` включает поля запроса, `finding_id`,
`configuration_id`, `device_id`, `source_sha256`, серверный UTC `created_at`
и фиксированный `actor="shared_service_token"`.

| Результат | HTTP |
| --- | --- |
| Новая запись и audit-event сохранены одной транзакцией | 201 |
| Тот же ID, scope, verdict и comment уже сохранены; возвращается исходная запись | 200 |
| ID занят другим намерением или finding hash не совпадает | 409 |
| Analysis/finding pair не существует | 404 |
| Неправильный body / превышен размер / неверный content type | 400 / 413 / 415 |
| Неверный токен / недоступная схема или повреждённый payload | 401 / 503 |

Параллельные повторы одного ID сохраняют одну запись и одно событие аудита.
ID не является секретом или отдельным правом доступа. Для изменения мнения
создавайте новый ID: предыдущая оценка остаётся в истории, PATCH/DELETE нет.
Оценки частичного анализа допускаются, но его risk остаётся null.

`GET /api/v1/findings/<finding_id>/feedback?analysis_id=<analysis_id>&limit=20&offset=0`
возвращает полные записи только этой пары, от новых к старым с ID tie-breaker.
`analysis_id` обязателен; `limit` 1–100, `offset` 0–10000. Offset может смещаться
при новых записях. Это история мнений, не автоматически выбранный итоговый verdict.

## Интерфейс и сбои связи

В деталях находки доступны verdict, comment и история по 20 оценок. Смена
находки/анализа очищает черновик; logout/reload очищает сессию, но сохранённые
оценки остаются в БД. Текст комментария рендерится как текст, не HTML.
UI проверяет version, actor, все target bindings и ID отправленного намерения.
Несогласованный ответ не отображается как успешно сохранённая оценка.

После неопределённой отправки обновите историю. Если тот же ID найден с тем же
содержимым, UI подтверждает сохранение и очищает только неизменённый черновик.
Повтор без изменения формы использует прежний ID; изменённый comment/verdict —
новое намерение с новым ID. ID хранится только в памяти этой формы, не переживает
reload или её закрытие: перед повтором после нового входа обязательно изучите
историю. Прерывание fetch не откатывает запись на сервере.

## Хранение и границы доверия

Payload оценок зашифрован Fernet и связан с типом/ID записи; при чтении сверяются
analysis, snapshot, device, source/finding hashes и открытые metadata строки.
Audit `finding.feedback_recorded` хранит ID оценки, action и timestamp, не comment
или verdict. SQL UUID, связи и время открыты. Шифрование не защищает от владельца
токена, компрометации ключа/процесса или удаления/сокрытия строк DB-admin.
Есть service RBAC и отдельный [operation journal](operation-audit.md), но нет
внешнего WORM-аудита, индивидуальной identity, независимой верификации эксперта,
rate limit, retention policy или общей квоты истории.

Unit/API/browser tests проверяют строгие контракты, привязки, конфликт/повтор ID,
конкурентные повторы, транзакционный rollback, encrypted restart-safe history,
неизменность анализа и stale responses. PostgreSQL-вариант проверяется отдельным
CI job и повторным desktop/mobile сценарием против Compose. Эти проверки не
измеряют качество инженерных меток или пригодность данных к обучению.
