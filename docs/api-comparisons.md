# Явные сравнения в постоянном API

Политики всегда запускаются. Сравнение с эталоном и peer-consensus добавляются
только по явному выбору оператора; автоматического выбора последней версии,
назначения роли или утверждения эталона нет. Сами сравнения не запускают ML/Batfish.
Дополнительно можно явно выбрать [статистическую модель](model-registry.md);
тогда результат имеет версию 0.3 (либо 0.4 при расширенном сравнении) и отдельный
statistical context.

По умолчанию API сохраняет детекторы сравнения 0.1.0. Для
[расширенной версии 0.2.0](expanded-comparisons.md) явно задайте
`comparison_version: "0.2.0"`; она доступна в API и в выборе области сравнения UI.
Старые сохранённые результаты не пересчитываются.

## Метки снимка

При загрузке можно добавить необязательное поле `inventory`:

```json
{
  "device_id": "00000000-0000-0000-0000-000000000001",
  "filename": "edge.cfg",
  "content": "hostname edge\n",
  "inventory": {
    "device_role": "edge-router",
    "site_class": "branch",
    "service_profile": "private-wan"
  }
}
```

Все три метки обязательны, если поле задано: 1–64 символа без крайних пробелов
и управляющих символов. Они сохраняются в зашифрованном canonical snapshot
как `device.role`, `device.site_class`, `device.service_profile`. Их не извлекает
парсер и не проверяет внешняя inventory-система. Метки относятся к конкретной
версии снимка; при загрузке новой версии их нужно явно передать снова.
Старые снимки не изменяются. Vendor/platform/hostname по-прежнему должны
соответствовать сохранённой identity UUID устройства.

## Выбор входов анализа

`POST /api/v1/configurations/{id}/analyze` принимает необязательный JSON:

```json
{
  "reference_configuration_id": "00000000-0000-0000-0000-000000000002",
  "peer_configuration_ids": [
    "00000000-0000-0000-0000-000000000003",
    "00000000-0000-0000-0000-000000000004",
    "00000000-0000-0000-0000-000000000005"
  ]
}
```

Это иллюстративные UUID: используйте IDs действительно сохранённых снимков.
Без тела или с `{}` сохраняется policy-only поведение `analysis-api-0.1.0`.
При выбранном сравнении 0.1 возвращается `analysis-api-0.2.0` и `comparison`
(0.3 при выбранной статистической модели). Явное `comparison_version: "0.2.0"`
с reference/peers возвращает `analysis-api-0.4.0` с `comparison-context-0.2.0`,
в том числе при совместном запуске со статистической моделью. Неизвестные версии
отклоняются; выбор версии без reference/peers не заявляет выполненное сравнение.
Запрос ограничен 16 KiB, неизвестные/повторяющиеся JSON-ключи отвергаются.
Авторизация выполняется до чтения тела, как и для загрузки.

- Эталон — другой снимок того же UUID, vendor/platform/hostname. Оба снимка
  должны быть полностью разобраны. Область фактов ограничена описанием
  [эталонного сравнения](expected-configuration.md).
- Группа — 3–20 полностью разобранных снимков других устройств с одинаковым
  ключом `vendor + platform + device_role + site_class + service_profile`.
  UUID, hostname и исходные hashes peers должны быть различны. Текущий UUID
  и hostname исключены. Это защита от повторного учёта версий/копий, не
  доказательство подлинности оборудования или независимости реальных сетей.
- Все выбранные снимки должны быть сохранены не позднее текущего снимка.
  Поэтому загрузите reference/peers перед candidate. Это порядок приёма
  в API, не подтверждённое время получения конфигурации с оборудования.
- Неполный текущий снимок допустим только для peer-триажа; риск остаётся `null`.
  В 0.2 все property features пропускаются, даже когда parser deficit не превысил
  порог и находок нет. В 0.1 сохраняется прежнее поведение частичных находок.
- Несуществующие, несовместимые или неоднозначные входы дают общий 400.
  Анализ и audit-event при этом не сохраняются; выбранная проверка не
  заменяется незаметно policy-only результатом.

## Сохранение и риск

`comparison.reference` и `comparison.peers` содержат IDs устройств/снимков,
SHA-256 и timestamps. `comparison.peer_baseline` хранит точный профиль консенсуса,
его версию, ключ группы, support counts и пороги. Всё находится внутри
зашифрованного analysis payload и сохраняется в одной транзакции с audit-event.
При чтении истории профиль не пересобирается по новым данным.
В версии 0.2 дополнительно сохраняется `comparison.peer_evaluation`: статус,
profile/compared/skipped features, parser-confidence-deficit proxy, exact findings
и SHA профиля. `omitted_features` профиля — отсутствие консенсуса, не parsing skip.
Ответ связывает профиль, report, source/device/status и находки. Эти связи
подтверждают согласованность артефактов, не истинность inventory или peer selection.
Отдельного registry профилей и автоматического refresh пока нет.

Каждая находка имеет `detector`, собственную версию и локальное объяснение,
сверенное с повторным запуском соответствующего детектора. Строки эталона
сохраняются отдельно от текущих affected lines; для удалений строки не выдуманы.

Без выбранной статистической модели в risk fusion входят только policy
и фактически выполненный peer detector.
Вес policy-only равен 1; при peers веса нормализованы до 0.7/0.3.
Критический policy guardrail сохраняется. Оценки не калиброваны.
Изменение эталонного факта не означает неисправности: `expected_configuration`
показывается как информация для review и не входит в итоговый риск.
Согласие peers не подтверждает безопасность и не меняет severity политики.

Старые зашифрованные анализы версии 0.1 остаются читаемыми; изменение схемы
таблиц или переписывание истории не требуется. Владелец общего API-токена
по-прежнему видит все снимки в пределах своей service role: это не персональная
identity, tenant isolation или организациями утверждённая baseline policy.

## Интерфейс

Заполните метки в форме загрузки. Откройте ранние снимки в истории:
«Выбрать как эталон» и «Добавить в группу сравнения». Затем откройте candidate
того же устройства и запустите анализ. Панель выбора относится к следующему
запуску; секция «Входы сравнения и профиль группы» — к сохранённому результату.
«Область сравнения» явно выбирает прежний 0.1 либо расширенный 0.2 набор.
Для сохранённого 0.2 результата отдельно показаны сравнения, parsing skips и
признаки без консенсуса. Источники новых findings закреплены за knowledge 0.3;
старые источники не заменяются новыми документами.
Выбор очищается при logout/reload, но inputs сохранённого анализа остаются в БД.

Проверки покрывают Cisco/JunOS reference, peers, совместный запуск, partial
target, отклонение несовместимых входов, ограничения тела, restart и отсутствие
вымышленных строк при удалении. Browser tests повторяются против SQLite и
Compose/PostgreSQL. Это функциональные проверки, не метрики качества детекции.

Отдельная `postgres-api` задача CI также запускает весь expanded integration
на PostgreSQL через явно заданный `NETCONFIG_TEST_DATABASE_URL`. Для каждого
сценария создаётся новая UUID-схема только в `postgresql+psycopg` базе с суффиксом
`_test`; после проверки удаляется только эта созданная схема. Без настройки
те же сценарии используют временную SQLite. Проверка CI-конфигурации сама по себе
не доказывает успешный PostgreSQL-прогон: результат относится к точному commit/run.
