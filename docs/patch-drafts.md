# Черновик изменения и проверка его актуальности

Модуль `app.patching` описывает уже подготовленную оператором пару конфигураций.
Он не генерирует команды, не соединяется с устройствами и не применяет изменения.
Состояние предложения фиксировано как `draft`; состояние его локального
рассмотрения — `needs_review`. Переходы в `validated`, `approved` и `applied`
в этой версии отсутствуют.

## Контракты и привязка версий

`create_patch_proposal(before, after, device_id=..., reference_id=...)`:

- проверяет бюджеты текста и совпадение vendor/platform/hostname;
- вычисляет SHA-256 обоих текстов в UTF-8;
- описывает вставки, удаления и замены диапазонами строк без исходного текста;
- создаёт детерминированный ID из содержимого метаданных предложения.

Одинаковые тексты не создают предложение. Комментарий или изменение переводов
строк являются изменением текста, даже если детекторы не находят семантической
разницы. При чтении файлов снимается UTF-8 BOM, но CRLF сохраняется: hashes
относятся к декодированному тексту, а не обязательно к побайтовому файлу с BOM.

Диапазоны `before_start:before_end` и `after_start:after_end` нумеруются с нуля,
правая граница не входит. Вставка имеет пустой диапазон до изменения, удаление —
после. Это координаты diff, а не однобазные `affected_lines` находок.
Сопоставление строк детерминированное, но минимальность diff не гарантируется,
особенно при большом количестве одинаковых строк.

`check_proposal_inputs` заново строит предложение из выбранных файлов.
Изменение текста любой стороны, UUID устройства или метаданных делает проверку
неуспешной. Нельзя взять результат для одной версии и применить его к другой.
Проверка привязки не аутентифицирует физическое устройство.

`review_patch_proposal` выполняет локальный preflight и связывает его hashes,
device ID и reference ID с предложением. `PatchReview` всегда содержит блокеры
`formal_verification_not_run` и `human_review_required`. Дополнительные блокеры
фиксируют неполный разбор, недоступное сравнение и нарушения политик.
Даже успешная локальная проверка не разрешает применение. Неполный разбор
допускает создание черновика, но не превращается в успешную верификацию.

## Создание и повторная проверка

После установки проекта; каталог назначения должен уже существовать:

```powershell
.venv\Scripts\python.exe -m app.patching.cli create --before previous.cfg --after candidate.cfg --device-id 7f64381c-fda8-48f9-8e8a-fb772b2f64dc --reference-id selected-v1 --output private-review.json
.venv\Scripts\python.exe -m app.patching.cli check --before previous.cfg --after candidate.cfg --device-id 7f64381c-fda8-48f9-8e8a-fb772b2f64dc --artifact private-review.json
```

`create` записывает только новый явно заданный `.json` через эксклюзивное
создание. Существующий файл не перезаписывается; родительские каталоги не
создаются. При сбое записи может остаться неполный файл: загрузчик отклонит
его; для повторного запуска используйте новое имя. Это не транзакционное БД-хранилище.

`check` только читает файлы. Он проверяет схему и контрольную сумму артефакта,
затем заново запускает локальные проверки на выбранных входах и сравнивает
весь отчёт. При изменении файлов, результатов парсера или каталога правил
нужен новый черновик/отчёт. Старый артефакт не исправляется автоматически.

Код `0` означает успешное создание или совпадение повторной локальной проверки,
**не разрешение на применение**. Код `2` — отказ без вывода содержимого входов.
Stdout содержит только идентификаторы, состояния и блокеры. Команд `apply`,
`approve`, `validate` и параметра принудительной перезаписи нет.

## Хранение и доверие

Артефакт — версионированный JSON с полезной нагрузкой `PatchReview` и SHA-256
её канонического JSON-представления. Размер ограничен 16 MiB. Входные конфиги
ограничены 2 MiB и 10 000 строк. Повторяющиеся JSON-ключи отклоняются.

Контрольная сумма выявляет повреждение, но **не является подписью**: человек
с доступом к файлу может пересчитать её. Поэтому загрузка сама по себе не
считается проверкой достоверности. `check` пересчитывает результаты, включая
случай, когда checksum модифицированного отчёта корректна.

Сырые команды, текст неизвестных строк и полный текстовый diff не сохраняются.
Однако находки preflight содержат адреса и имена сетевых объектов. Артефакты
не обезличены и не зашифрованы модулем: сохраняйте их в закрытом каталоге с
доступом на уровне ОС, не публикуйте в Git и не отправляйте внешним сервисам.
Готовый защищённый production storage, подпись, роли и журнал аудита отсутствуют.

## Проверки реализации и дальнейшая граница

Тесты покрывают Cisco и JunOS, шесть структурных мутаций, диапазоны вставки/
удаления/замены, CRLF, устаревшие входы, сохранность файлов, повреждение JSON,
подмену отчёта с пересчитанной суммой и отдельный запуск CLI.
Все данные лабораторные; это не метрики production-качества.

Следующий блок — настоящий verifier с явным набором проверок и топологией.
Без его проверяемого результата и решения инженера никаких повышений статуса
не будет. В этой версии Batfish не запускался и сетевая достижимость не проверялась.
