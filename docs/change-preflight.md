# Локальная проверка изменения конфигурации

`app.verification.preflight.review_configuration_change` объединяет уже
реализованные локальные проверки для двух снимков одного устройства.
Это подготовка к проверке изменений, не Batfish adapter и не формальная
верификация. Результат всегда требует рассмотрения инженером.

## Что выполняется

1. Повторная валидация канонических моделей и проверка совпадения vendor,
   platform и hostname. UUID устройства и ID выбранного эталона задаёт оператор.
2. Выполнение одной версии каталога политик для каждого снимка.
3. Сопоставление нарушений: `introduced`, `resolved`, `persistent`.
4. Сравнение поддерживаемых BGP/OSPF/интерфейсных фактов с выбранным эталоном.
5. Отдельная оценка риска текущего снимка только по политикам.

Отклонения от эталона не передаются в risk fusion: отличие от ожидаемого
параметра не равнозначно нарушению политики. Остальные источники риска
помечены недоступными существующей формулой; веса перераспределяются.
Это не калиброванная вероятность аварии. ML не запускается.

## Сопоставление нарушений

Ключ включает категорию правила, severity, observed и expected. Сравнивается
точное содержимое значений; массивы сохраняют порядок. Изменение значения
может дать пару «старое исчезло / новое появилось», а не исправление.
Название, номера строк, provenance и finding ID не входят в ключ: комментарий
перед конфигурацией не должен создавать ложные новые нарушения.

Повторяющиеся одинаковые нарушения учитываются по количеству. Общие
экземпляры сопоставляются в порядке строк-доказательств; это не доказательство
непрерывной идентичности конкретного повторяющегося объекта. Каталоги разных
версий или находки разных устройств смешивать нельзя.

У `persistent` отдельно сохраняются `before` и `after`. У `resolved` строки
относятся к предыдущему снимку; у `introduced` — к текущему. Finding ID может
совпадать между снимками, поэтому его нужно читать в контексте стороны и hash.
`resolved` означает отсутствие прежнего наблюдения в поддерживаемом разборе,
а не доказанную безопасность изменения.

## Неполный разбор

Предупреждения, неизвестные команды либо parser confidence ниже 1 хотя бы
в одном снимке отключают классификацию изменений политик (`policy_changes=null`)
и сравнение с эталоном (`reference_status=unavailable`). Доступные находки
политик обоих снимков остаются в отчёте как частичные результаты.
Если текущий снимок разобран не полностью, `current_policy_risk=null`.
Неоднозначные ключи эталонных фактов также дают `unavailable`, а не пустой успех.

`PreflightReport` фиксирует hashes входов, версию отчёта и каталога, ID устройства,
ID эталона, сводки полноты разбора, доказательства и ограничения. ID отчёта
детерминирован для одинаковых канонических входов и hashes, не зависит от
времени чтения. Это не подпись и не персистентный журнал аудита.
Неизвестные исходные строки и полный текст конфигурации в отчёт не включаются.

Поля `review_status=needs_review`, `formal_verification=not_run`,
`ml_status=not_run` и `requires_human_review=true` фиксированы контрактом.
Ни нулевой риск, ни пустой список находок не дают `validated` или `approved`.

## Запуск

После установки проекта в виртуальное окружение:

```powershell
.venv\Scripts\python.exe -m app.verification.preflight_cli --before previous.cfg --after candidate.cfg --device-id 7f64381c-fda8-48f9-8e8a-fb772b2f64dc --reference-id selected-snapshot-v1
```

Команда читает только явно выбранные локальные файлы, использует общий
ограниченный UTF-8 reader (2 MiB, 10 000 строк, `.cfg`/`.conf`/`.txt`) и выводит
JSON в stdout. Нет подключения к оборудованию, сети или записи изменений.
При ошибках чтения/парсинга в stderr не печатаются исходные значения и пути.
Аргументы командной строки не предназначены для передачи секретов.

| Код | Значение | JSON-отчёт |
|---|---|---|
| 0 | Поддерживаемые проверки завершены, сигналов для рассмотрения не найдено | Есть; не разрешение на применение |
| 1 | Есть текущие нарушения, изменения политик или эталонных фактов | Есть |
| 2 | Невалидный вход, ошибка чтения или несовпадение устройства | Нет |
| 3 | Проверки выполнены частично | Есть, с недоступными результатами |

Даже неизменённая конфигурация с нарушениями возвращает 1. Исправление
наблюдавшегося нарушения тоже возвращает 1: оно должно быть рассмотрено.

Отчёт может содержать IP-адреса, имена сетевых объектов и значения параметров.
Он не обезличен: храните его закрыто и не публикуйте в репозитории. Текстовый
diff намеренно не выдаётся, чтобы не копировать секреты из исходных строк.

## Границы завершённого этапа

Реализованы локальный сервис, CLI и тесты поведения до/после для Cisco и JunOS.
Тесты включают реальные отдельные запуски CLI, ошибки входа, частичный разбор,
сдвиг строк, повторяющиеся нарушения и запрет фиктивного формального статуса.
Это функциональные лабораторные проверки, не оценка качества на production.

Следующий этап: отдельный контракт patch proposal и результатов verifier с
привязкой к hashes до/после. Batfish, проверки достижимости, хранение и
утверждение инженером ещё не реализованы.
