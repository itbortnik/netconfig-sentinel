# Нативный черновик из сохранённой находки

API/UI-сценарий локально проверен для поддержанных Cisco/JunOS originals:
создание кандидата, безопасный отчёт, reader history и чтение после удаления
исходной загрузки и фактического перезапуска процесса. Реализация и границы
evidence независимо проверены. [Функциональный отчёт](evaluation/owned-native-functional.json)
описывает четыре запуска двух авторских семей в двух размерах экрана.

Отдельный путь использует существующий [ограниченный генератор](vendor-patch-drafts.md)
для `management.telnet_enabled`: точный сохранённый Cisco IOS/IOS-XE либо flat JunOS
original → выбранная находка policy engine → новый текстовый кандидат и local review.
Языковая модель для этого пути не требуется. Текущий original служит локальной
точкой сравнения; утверждённым baseline он не становится.

Для создания нужны роль `engineer` или `admin`, сохранённый исходный текст,
полный поддержанный разбор и два отдельных явных согласия: на локальную генерацию
и на хранение точных закрытых копий before/candidate. Эти копии могут содержать
неизменённые пароли, SNMP communities и другие данные исходника. Они шифруются
в БД и сохраняются независимо от строки `configuration_sources`: удаление только
этой строки не удаляет копии в истории черновика.

## API и привязки

`GET /api/v2/configurations/{configuration_id}/native-patch-selection/{analysis_id}`
возвращает hashes выбранного analysis, canonical snapshot и текущих Telnet findings.
Этот read не читает raw original и не подтверждает его наличие или возможность
генерации. Клиент передаёт эти точные pins и новый `candidate_id` в
`POST /api/v2/configurations/{configuration_id}/native-patches` с явной версией
`native-patch-request-0.1.0` и обоими согласиями. Raw content от клиента не принимается.

Новая генерация проверяет snapshot/device/source/canonical/analysis/catalog/finding,
заново разбирает retained original и сопоставляет свежие policy findings. Затем
существующий генератор действительно создаёт candidate, повторяет разбор и policy
проверку обеих сторон и формирует local review. Неоднозначный transport context,
неподдержанный синтаксис, неполный разбор и устаревшие pins дают отказ.

`GET` той же коллекции выдаёт summaries, `GET .../{candidate_id}` — безопасный
типизированный отчёт с фиксированными inspection-командами. Публичный ответ
не содержит полных исходников или raw diff. Список команд выводится из разрешённых
типов edits и числовых VTY-диапазонов.

Миграция `0018_native_patch_candidates` добавляет отдельную зашифрованную историю.
Сохранение результата и `native_patch.created` атомарно. Повтор того же UUID,
configuration URL и запроса возвращает первый результат с первоначальными ролью,
временем и proof; смена intent даёт `409`. После неопределённого ответа `503`
следует проверить сохранённую запись и повторять тот же intent, сохраняя UUID.
Доступ к истории использует существующий общий scope сохранённых устройств.

При чтении проверяются encrypted row binding, SQL metadata, весь public proof,
сохранённые родители и точное разрешённое текстовое изменение, включая hashes,
anchors и ChangeSpan. Чтение и replay не запускают текущий parser/policy/generator
и работают после удаления original-source строки. Hash integrity подтверждает
связность сохранённых данных, а не достоверность разметки или личность инженера.

## Границы результата

Результат всегда `needs_review`, formal qualification — `not_proven`;
`calibrated`, `quality_proven`, `individual_identity_verified`, `approved`, `applied`
остаются false. Полнота локального parser не подтверждает vendor syntax, SSH access,
ключи, AAA, rollback или свойства сети. Все соответствующие блокеры видимы.

Этот путь пока не создаёт after snapshot, обычный object draft или model draft,
не экспортирует raw candidate и не запускает Batfish/ML. Команды не выполняются;
подключения к устройствам и применения конфигураций нет. Отдельные существующие
offline-сценарии не являются проверкой нового сохранённого кандидата.

Локальные проверки используют две авторские семьи примеров Cisco/JunOS и проверяют
работу программы и сохранение истории. Независимое качество на реальных данных,
формальная проверка, безопасный доступ к реальному устройству и approval ими
не подтверждены.

Полный локальный backend-набор: 5483 pass / 60 skip, coverage 92%. Извлечённый
wheel с теми же 319 runtime-файлами и тремя UI-assets прошёл 1748 pass / 42 skip
на каждой Pydantic 2.13.5, 2.14.0 и 2.14.1. UI: 983 unit и 410 browser checks,
включая четыре actual HTTP случая и 16 новых mock component controls; прочие
390 — регрессии существующих сценариев. Повторы и размеры экрана не увеличивают
независимый корпус. Два новых PostgreSQL opt-in случая локально skipped:
тестовая база не выбрана; live engine для этого пути не запускался.
